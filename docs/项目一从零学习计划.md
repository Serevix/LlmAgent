# 项目一学习内容：从业务问题到后端实现

这份学习材料对应当前仓库，以后端为重点，不按天数安排。先理解项目要解决的问题和各层职责，再沿着“注册与会话 → 导入书籍 → 检索 → LangGraph 回答 → 评测”读代码。前端只用来辨认请求入口和结果展示。每读完一段，都要回答：谁调用它？输入来自哪里？输出给谁？为什么放在这一层？失败后会怎样？

## 生成图片与 Word 的工具链（2026-10-22）

现在共有三个业务工具：`search_book_chunks`、`generate_image`、`generate_word`。书籍检索仍由 retrieve 节点固定调用；两个生成工具由所选聊天模型通过 bind_tools 自主选择，再由后端执行。普通 RAG 提问沿用原路径，生成或导出候选才增加工具规划请求。每轮最多各生成一张图片和一份 Word。

### 阅读顺序与每个函数的职责

| 顺序 | 文件与函数 | 这个函数接收哪些数据、怎样传递、为什么这样设计 |
| --- | --- | --- |
| 1 | `agents/artifact_planner.py` 的 `may_need_artifact` | 接收本轮问题，先做本地候选筛选；普通提问不必每轮请求一次模型来选择工具。候选不等于一定执行，最终看模型的 tool_calls。 |
| 2 | 同文件 `plan_artifacts` | 接收所选模型、受限近期消息、摘要、预算；bind_tools 暴露两个工具，再验证工具名、数量、公开参数和长度。只返回工具计划，不在这里生成文件。 |
| 3 | `agents/artifact_tools.py` 的 `generate_image`、`generate_word` | 模型填写画面描述、标题，或 Word 模式及检索问题。InjectedToolArg 隐藏身份、会话、幂等键、可信正文和来源，后端在执行时补入。 |
| 4 | `chat_graph.py` 的 `plan`、`route_from_plan` | 图片及已有答案导出直接进入 run_artifact_tools；新主题 Word 先进入原来的 retrieve → grounded_answer/no_evidence，再由条件边进入生成节点。 |
| 5 | `grounded_answer` 与 `latest_verified_answer` | 新知识文档只生成正文并核对书籍依据；导出旧答案直接读取最近一条已核对正文，无须重新生成。没有依据时不导出知识文档。 |
| 6 | `run_artifact_tools` | 根据模型选择执行工具，覆盖注入认证 user_id、配置中的 thread_id 和本次 request_id；文件节点不整节点重试。新知识文档完成后用相同 AIMessage.id 覆盖消息，维持一问一答。 |
| 7 | `services/artifact_service.py` 的 `create`、`public`、`storage_path` | 先按请求键查询已有结果，再生成和保存。服务器生成真实路径，generated_artifacts 记录元数据，public 只返回附件信息；下载时还要检查根目录边界。 |
| 8 | `artifacts/images.py` 的 `generate_image_bytes`、`validate_image_url`、`validate_image` | 调用独立的硅基流动图片模型，下载临时图片，限制域名、大小与像素并验证格式；下载请求不携带图片 API Key。原始字节保存以保留服务商水印。 |
| 9 | `artifacts/word.py` 的 `word_bytes`、`add_inline`、`clean_xml_text` | 接收后端认可的正文和引用，将 Markdown 标题、加粗、列表、代码与表格转成 docx，移除非法 XML 字符，再附书名和页码/段号。只排版，不额外调用 LLM。 |
| 10 | `api/v1/files.py` 的 `file_content` | 从认证身份按归属查记录，验证存储位置，返回 FileResponse。知道文件 ID 不代表拥有下载权限。 |
| 11 | `chat.py` → `api.ts` → `ArtifactCard.tsx` | API 将附件写入 artifacts 事件与历史响应；streamChat 调 onArtifacts 更新消息。artifactBlob 用 Bearer 取二进制，ArtifactCard 显示图片并触发下载，卸载时释放 Blob URL。 |

### 模型能选择业务参数，可信数据由程序注入

```python
# artifact_planner.py：原生工具调用，模型决定是否调用及使用什么公开参数。
response = await model.bind_tools(list(ARTIFACT_TOOLS.values()), tool_choice="auto").ainvoke(
    prompt, max_tokens=limits.CONTEXT_AUX_MAX_OUTPUT_TOKENS)

# chat_graph.py：经验证的工具参数在前，后端可信参数在后，覆盖注入身份和正文。
artifacts.append(await ARTIFACT_TOOLS[name].ainvoke({**call["args"], **injected}))
```

Word 的 `content_source='latest_answer'` 导出最近已核对答案，`content_source='knowledge'` 先检索并核对新正文。新正文的生成输入使用工具规划出的知识问题，避免把“生成文件”交给回答模型处理；文件生成交给后端。已有问答的 messages 不被这个模型输入视图替换，历史原话继续保留。

### 三条数据链

```text
生成图片：用户问题 → plan → plan_artifacts → 模型返回 generate_image 工具调用
→ route_from_plan → run_artifact_tools → generate_image.ainvoke
→ ArtifactService.create → 硅基流动图片 API → 下载并验证 → 文件落盘与元数据入库
→ AIMessage.additional_kwargs["artifacts"] → SSE artifacts → 前端图片预览与下载

导出旧回答：用户问题 → 模型选择 generate_word(latest_answer)
→ latest_verified_answer 锁定正文及来源 → run_artifact_tools 注入正文
→ generate_word.ainvoke → word_bytes → 文件与数据库 → SSE 附件

新主题 Word：用户问题 → 模型选择 generate_word(knowledge, question)
→ retrieve（BM25＋向量＋RRF＋rerank）→ grounded_answer（生成正文＋依据核对）
→ run_artifact_tools → Word 附件；若无证据或核对失败，则保留弃答且不创建文档
```

新增业务表是 `generated_artifacts`；文件默认保存在 `backend/data/generated/<user_id>/`。图片模型单独配置，沿用用户确认的现有硅基流动账号；切换聊天模型不会切换图片模型。前端仍为两页，通过自然语言触发工具，附件直接显示在聊天消息下方。

验证时读 `tests/test_artifacts.py`：包括真实图调度、工具选择、Word 依据限制、后端身份注入、同请求复用、SSE/历史恢复、文件越权和路径边界。模型烟测报告同时保留成功与弃答样例，不能把工具运行成功当成所有知识问题都能回答。功能依赖聊天模型支持原生工具调用；当前请求内生成，没有后台任务队列或断线续传。生成图片是创作，不能当成知识库事实来源。

## LangGraph 自动重试：只读检索最多执行两次（2026-10-22）

先读 `backend/app/agents/retry.py`，再看 `chat_graph.py` 的 `retrieve` 和 `builder.add_node("retrieve", ...)`，最后读 `tests/test_graph_retry.py`。LangGraph 只在节点抛出符合条件的异常后重跑该节点；捕获异常并返回空字典属于正常结束，不会触发自动重试。

```python
# retry.py：max_attempts 包含第一次执行；首次失败后只再试一次。
RETRIEVAL_RETRY_POLICY = RetryPolicy(
    max_attempts=2,
    initial_interval=0.5,
    backoff_factor=1.0,
    max_interval=0.5,
    jitter=False,
    retry_on=RetryableRetrievalError,
)

# chat_graph.py：策略挂到只读检索节点上。
builder.add_node("retrieve", retrieve, retry_policy=RETRIEVAL_RETRY_POLICY)
```

数据怎样传递：`graph.astream` 调度 `retrieve` → `search_book_chunks.ainvoke` → 新建数据库会话 → `KnowledgeService(embedding_max_retries=0).search` → Embedding、Milvus、rerank。若遇到临时故障，`is_transient_retrieval_error` 识别异常类型或状态码，`retrieve` 抛出不含原始服务商信息的 `RetryableRetrievalError`，LangGraph 等待 0.5 秒后用同一节点输入再执行一次。成功才提交本轮 rag_context/sources，再进入生成和核对；它不会从 START 重跑整个流程。

重排错误 `RerankError.retryable` 区分临时超时/限流与密钥/格式错误。找不到证据、参数错误、鉴权错误和不合格返回格式均不触发节点重试。持续故障耗尽两次尝试后，`chat.py` 将安全异常转为 HTTP 502 或 SSE error，不把服务故障说成知识库依据不足。

为什么只给检索加：检索是只读操作，重复执行不会重复保存记忆；回答生成已经向用户发送文字后重跑会导致重复内容。图内 Embedding 关闭 SDK 重试，避免与节点重试相乘；导入和独立检索的默认 SDK 重试仍为两次。Milvus SDK 在一次调用的超时范围内仍可能内部重试，因此“节点最多两次”不是所有底层网络请求总次数的硬上限。摘要、改写、核对和记忆继续沿用各自的降级或 SDK 重试处理。

## 问答调用优化：先判断是否需要辅助任务（2026-10-22）

普通问题现在默认只请求 **回答生成＋书籍依据核对** 两次聊天模型。以前首轮还会提炼长期记忆，共 3 次；有前文时再改写问题，共 4 次。Embedding 和 rerank 仍是额外的模型服务请求；Milvus BM25 和 RRF 不调用聊天模型。

阅读顺序：先看 `backend/app/agents/call_policy.py` 的 `needs_query_rewrite` 和 `needs_memory_extraction`，再看 `chat_graph.py` 的 `plan`、`route_after_answer`、`_save_memory`，最后看 `tests/test_chat_latency.py` 的实际图测试。规则不决定能否回答，只筛选是否有必要请求辅助模型；书籍依据核对继续独立执行。

```python
# chat_graph.py 的 plan：独立问题无需花一次请求去重复原问题。
has_history = len(recent) > 1 or bool(state.get("conversation_summary"))
if not needs_query_rewrite(latest, has_history, rewrite_mode):
    return {"route": "book_search", "search_query": latest,
            "rag_context": "", "sources": []}

# 回答或弃答后由条件边决定是否保存记忆，普通问题直接 END。
builder.add_conditional_edges("grounded_answer", route_after_answer)
builder.add_conditional_edges("no_evidence", route_after_answer)
```

| 场景 | 默认怎样走 | 聊天模型请求数（未触发摘要，且核对正常执行） |
| --- | --- | --- |
| 独立书籍问题，含已有历史的独立问题 | 本地规则 → 原问题检索 → 生成 → 核对 → END | 2 |
| “它有哪3种用途？”且有前文 | 改写（仍读摘要及近期消息）→ 检索 → 生成 → 核对 → END | 3 |
| 明确表达学习目标/偏好或要求记住 | 上述链路后，模型提炼 MemoryDecision，再按结果写 Store | 增加 1 |
| 独立问题未检索到证据，且不含记忆信息 | 检索 → no_evidence → END | 0；检索本身仍可能请求 Embedding/rerank |

`CHAT_QUERY_REWRITE_MODE=auto` 和 `CHAT_MEMORY_MODE=selective` 是默认值，配置 `always` 可以分别恢复旧策略；记忆还可设为 `off`。筛选规则可能漏判含蓄的追问或偏好，这是减少辅助调用的取舍，并不是通用语言理解器。上下文摘要仍在预算阈值触发，只处理新增旧消息。

性能要区分首字（未核对草稿）、最终答案和 done：两题实测的聊天请求由 3/4 次降为 2/2 次，第二轮首字从 16.23 秒降到 3.05 秒；首轮却从 3.34 秒升到 5.40 秒，整体耗时没有稳定下降，说明网络、输出长度和模型负载仍有明显影响。详见 `backend/evals/chat_latency_before_20261022.json` 与 `chat_latency_after_20261022.json`；`benchmark_chat.py` 可复测，不能把这个小样本当作固定提速比例。普通问答不再等待额外的长期记忆请求，含记忆信息的消息仍会等待提炼完成。

## 检索链更新：BM25、RRF 与 rerank（2026-10-22）

默认检索现在是 **Milvus 原生稠密向量＋BM25 → RRF 融合 → 硅基流动 rerank → 合格证据与同书上下文 → 图内生成与依据核对**。下文早期的“余弦前五＋0.55 阈值”属于保留的 dense 基线；不能把它当作当前默认链路。

### 先看什么，再看什么

| 顺序 | 文件与函数 | 重点理解 |
| --- | --- | --- |
| 1 | [types.py](../backend/app/rag/types.py) 的 RetrievedChunk | score_type 说明当前 score 的含义，dense_score/fusion_score/rerank_score 分开保存；is_expansion 表示同书补取上下文。 |
| 2 | [milvus_store.py](../backend/app/rag/milvus_store.py) 的 _ensure_collection | text 启用 jieba 中文分词和 lowercase；BM25 Function 从 text 自动生成 sparse，稠密与稀疏索引保存在同一实体中。 |
| 3 | 同文件的 _hybrid_search | 两个 AnnSearchRequest 使用同一 user_id/book_ids 过滤；RRFRanker 根据两路排名融合并去重。RRF 不是把余弦分数和 BM25 分数直接相加。 |
| 4 | [knowledge_service.py](../backend/app/services/knowledge_service.py) 的 search 与 _expand_candidates | 先查 ready 书籍并向量化问题，融合后对符合条件的数量问题补取短书，合并去重后整体重排。不能提前用 0.55 排除低余弦但关键词匹配的候选。 |
| 5 | [reranker.py](../backend/app/rag/reranker.py) 的 rerank | 问题和片段原文发送到硅基流动 /rerank；返回 index 对应提交的 documents 位置，校验数量、编号和分数后恢复片段。 |
| 6 | 回到 search，再看 tools.search_book_chunks 与 graph.retrieve | 普通问题保留重排合格前 K 项；短书已被命中时附带有界上下文，工具传递分阶段分数，图继续控制证据长度和最终核对。 |
| 7 | [migrate_index.py](../backend/app/rag/migrate_index.py) 的 migrate、snapshot、row_digest | 复制旧向量与片段，核对逐 ID 内容摘要及来源稳定性，烟测后才发布新别名；旧集合不删除、不双写。 |
| 8 | [test_hybrid_retrieval.py](../backend/tests/test_hybrid_retrieval.py) 与 evaluate.py | 观察关键词候选保留、去重、短书覆盖、重排异常和迁移失败不发布；用三种策略对比同一标注集。 |

### 一次问题的实际函数调用

```text
chat_graph.retrieve
→ search_book_chunks.ainvoke
→ KnowledgeService.search
  → books.list_ready_ids
  → EmbeddingService.embed([question])
  → MilvusBookStore.hybrid_search → _hybrid_search
      → AnnSearchRequest(vector/COSINE) ＋ AnnSearchRequest(sparse/BM25)
      → MilvusClient.hybrid_search(ranker=RRFRanker(k=60))
  → _expand_candidates（符合条件的短书数量问题才补取）
  → Reranker.rerank
      → HTTP POST /rerank(query, documents, top_n)
      → 按 index 找回原片段，保留 fusion_score，新增 rerank_score
  → 重排阈值筛选与前 K 选择，附加标记过的同书上下文
→ 工具转换字典 → retrieve 构造 rag_context 和 sources
→ grounded_answer → 流式草稿 → evidence_supports_answer → 最终结果
```

关键代码摘录：

```python
# 两路先融合，数量问题补取后，全部候选一起重排。
candidates = await self.vectors.hybrid_search(user_id, query_vector, question, book_ids)
candidates = await self._expand_candidates(session, user_id, question, query_vector, candidates)
ranked = await self.reranker.rerank(question, candidates)
qualified = [hit for hit in ranked if hit.score >= settings.RERANK_MIN_SCORE]
```

RRF 对每一路名次计算 `1/(k+rank)` 后求和，使用排名是为了避免两种原始分数的量纲差异。rerank 则同时读取问题和候选原文，重新判断相关性。两者都不能代替回答依据核对。

阈值分别解释：`RAG_MIN_SCORE=0.55` 仅用于 dense 基线；RRF 不套用这个阈值；`RERANK_MIN_SCORE=0.30` 是重排的初始阈值，需要用语料校准。低分 `is_expansion` 片段是短书上下文，并非独立通过阈值的命中。图的窗口预算仍可能限制完整列举内容，因此不能承诺所有跨页条目一定被纳入。

### 迁移与验证结果

已有资料先停止所有写入，再运行 `python -m app.rag.migrate_index --report evals/hybrid_index_migration.json`。迁移保留片段 ID、原文和已有向量，不重新调用 Embedding；逐行校验成功后发布 `MILVUS_HYBRID_COLLECTION` 别名。本机本次迁移 228 个片段，旧集合保留。其他机器或端口的写入也要暂停，端口检查不等于分布式锁。

2026-10-22，同一用户的 5 本 ready 资料、15 道标注题（10 正例、5 负例）对比：

| 模式 | Hit@5 | MRR@5 | 检索层弃答准确率 | P50 / P95 |
| --- | --- | --- | --- | --- |
| dense | 1.00 | 0.6533 | 0.60 | 271 / 805 ms |
| hybrid | 0.90 | 0.6750 | 0.00 | 286 / 1015 ms |
| hybrid_rerank | 1.00 | 1.0000 | 1.00 | 1004 / 1420 ms |

报告在 `backend/evals/hybrid_ablation_20261022.json` 及三份逐题 JSON 中。Hit@K/MRR@K 仅计算前 K 项，额外同书上下文的数量另记 returned_count。这是小型既有标注集的结果，不是独立留出集，更不是所有问答准确率或零幻觉保证。重排增加接口请求、费用及延迟；调用失败明确报错，不静默退回没有重排的结果。

### 4. 三段核心代码要会读，也要能写出骨架

代码只保留关键骨架；下面函数名与实际实现对应，省略号代表省略内容，不能直接复制运行。

```python
# chat_graph.py：摘要节点传入旧状态，返回局部状态更新。
return await context_manager.prepare(
    state["messages"],
    state.get("conversation_summary", ""),
    state.get("summarized_count", 0),
)
```

应解释：三个参数分别来自 checkpoint 中的完整历史、旧摘要和进度；返回字典没有 messages，因此不会删除完整历史；后续 plan 使用更新后的摘要和近期消息。

```python
# model_service.py：模型独立，历史存储共享，预算不改全局 settings。
async with self.runtime_model(spec) as model:
    limits = ContextLimits.from_settings(spec.context_window, spec.max_output_tokens)
    yield build_chat_graph(model, app.state.checkpointer, app.state.store,
                           limits=limits, structured_output_method=spec.structured_output_method)
```

应解释：async with 管理客户端生命周期，yield 把图交给调用者；图消费完毕再关闭客户端；thread_id 由 chat.py 传入。不是“共享一个模型、临时改它的 Key”。

```python
# chat.py：图事件转为 SSE；模型文字增量来自图内的 model.astream。
async for mode, payload in graph.astream(
    {"messages": [HumanMessage(content=data.message)]},
    config=config, context=context, stream_mode=["custom", "updates"],
):
    ...
```

应解释：model.astream 获取回答增量；writer 发送 custom 事件；graph.astream 收集图事件和节点更新；yield SSE 字符串是 HTTP 传输层。最终 answer 覆盖草稿并不是“再次调用模型生成同一份回答”。

## 先建立分层地图

| 层 | 本项目中的职责 | 不要混淆的边界 |
| --- | --- | --- |
| API：api/v1 | 把 HTTP 请求解析为 schema，注入当前用户和数据库 session，返回状态码与响应。 | 不负责解析 PDF、生成向量或写复杂业务规则。 |

prepare 的入口核心代码：

```python
messages = dialogue_messages(history)
cursor = min(max(0, summarized_count), len(messages) - 1)
summary = clip_text(summary, limits.CONTEXT_SUMMARY_MAX_TOKENS)
active = messages[cursor:]
total = message_tokens(active) + text_tokens(summary)
if total > limits.CONTEXT_SUMMARY_TRIGGER_TOKENS:
    tail = recent_start(active, limits.CONTEXT_HISTORY_BUDGET_TOKENS,
                        limits.CONTEXT_RECENT_MESSAGES)
    target = cursor + tail
```

`cursor` 表示已摘要的用户/AI 消息数量，不是 token 数。例如有 21 条消息，cursor=10，tail=6，则 target=16：前 10 条已经覆盖在摘要中，本轮处理 messages[10:16]，近期 messages[16:21] 保留原文。数字是说明切片边界的例子，实际取决于文本长度。阈值超出但 tail=0 时没有更早消息可摘要，不会凭空生成摘要。

prepare 中每个摘要请求的实际输入与输出：

```python
prompt = [SystemMessage(content=SUMMARY_RULES),
          HumanMessage(content="已有摘要：\n" + updated + "\n\n新增对话：\n" + batch)]
ensure_input_budget(prompt, limits.CONTEXT_SUMMARY_MAX_TOKENS, limits)
response = await self.model.ainvoke(
    prompt, max_tokens=limits.CONTEXT_SUMMARY_MAX_TOKENS,
)
```

这里用 ainvoke：下游需要完整摘要，不需要向用户展示摘要文字增量。所有批次成功后才执行 `summary, cursor = updated, end`；失败时不能谎称这些消息已经处理成功。

最终准备视图的实际代码：

```python
active = messages[cursor:]
start = recent_start(active, limits.CONTEXT_HISTORY_BUDGET_TOKENS)
return {"conversation_summary": summary, "summarized_count": cursor,
        "context_messages": active[start:]}
```

返回字典更新图状态，不包含 messages，所以完整历史不被删除。最后这次 recent_start 没传 count，只按预算取近期消息，不是永远固定八条。摘要、游标与模型视图也在同一 thread_id 的 checkpoint 中；下一轮重新计算模型视图。它们没有写入跨会话的 Store。

## 第二条完整数据链：一本书怎样进入 Milvus

从 [knowledge.upload_book](../backend/app/api/v1/knowledge.py) 开始。它获取当前用户，调用 KnowledgeService.upload，然后把 process(book.id, user_id) 放进 BackgroundTasks。upload 保存原件与 KnowledgeBook，并立即返回 processing 状态。process 使用**新的数据库 session**继续：

~~~python
contents = await asyncio.to_thread(Path(book.storage_path).read_bytes)
~~~

## 第三条完整数据链：用户问题怎样得到有依据的回答

从 [chat_stream](../backend/app/api/v1/chat.py) 开始。请求体只有 conversation_id 和 message；身份由 token 解析，thread_id 由数据库记录取得。API 调用图的核心数据关系是：

~~~python

        print(payload)
    elif mode == "updates":
        # 节点执行完成后的状态更新，其中包含核对后的最终答案。

~~~

这段为便于追踪，省略了 API 的异常处理及 event_stream 包装。messages 进入 ChatState；config 让图读写该会话的 checkpoint；context.user_id 让工具只查当前用户的书。图的固定路径是：

~~~text
START → manage_context → plan → retrieve → grounded_answer 或 no_evidence → save_memory → END
~~~

manage_context 先构造摘要和近期消息视图，plan 产生 search_query；retrieve 通过 search_book_chunks 调 KnowledgeService.search。search 先从 PostgreSQL 取当前用户 ready 书籍 ID，再把 question 向量化，Milvus 按 user_id 和 book_ids 过滤命中，最后按 RAG_MIN_SCORE 筛选。retrieve 将正文拼成编号 rag_context，将书名、页码、分数等放在 sources。无 sources 时走 no_evidence；有命中时，grounded_answer 才要求模型依据片段作答并标注编号，然后 evidence_supports_answer 检查引用和内容。失败时返回固定弃答并清空来源。

对于“6 个算法”“8 种框架”这样的**明确数量列举问题**，首轮直接保留原问法；有前文时允许补全指代，并要求改写保留数量与专业名称。检索先走正常的全库前 5 名；若最高命中得分至少 0.70，且所属书籍已就绪、片段数不超过 24，KnowledgeService.search 会在 Milvus 中再查这一本短文档的全部片段，并按页码提供给图。这是因为列表常分散在多页，前 5 个相似片段不足以列全；它不放宽普通问题的全局阈值。低置信度命中或长书仍按常规检索处理，依据核对与弃答规则保持不变。对应判断在 [query.py](../backend/app/rag/query.py) 和 KnowledgeService.search 中。

## 上下文管理：为什么不再把完整历史传给模型

模型选择增加后，先补看 [schemas/model_profile.py](../backend/app/schemas/model_profile.py)、[api/v1/models.py](../backend/app/api/v1/models.py)、[ModelService](../backend/app/services/model_service.py)。前端选择配置编号作为 ChatRequest.model_id 发送；服务检查该配置属于当前用户，解密密钥，再创建本次请求的模型。runtime_graph 复用 app.state.checkpointer 和 Store，所以仍按原 thread_id 读取历史。模型参数不进入 ChatState，API Key 不会成为会话消息。列表响应排除明文和密文凭据，数据库仅保存加密值。

默认请求复用原 app.state.chat_graph；选择自定义模型时，runtime_graph 为同样的节点结构编译一份请求级图。ContextLimits.from_settings(window, output) 为该图分配独立预算，小窗口缩小历史、摘要和书籍证据，不修改全局 settings。ensure_input_budget 和 ContextManager 接受同一份 limits；核对模型也使用它。这避免用户 A 选择小窗口模型时影响正在执行的用户 B 请求。

学习调用链：输入框左侧 ModelControls → 保存参数或选择 model_id → streamChat 请求 → chat_stream 校验会话和模型所有权 → ModelService.runtime_graph → 原 LangGraph 工作流 → SSE → 原历史展示。模型面板使用 portal，表单提交不冒泡到聊天发送表单；切换模型只改变 selectedModel，不修改 selected 会话和 messages。连接测试独立于聊天图，不向历史添加测试消息。具体回归测试见 [test_models.py](../backend/tests/test_models.py)。

**已有两组服务端 Key 怎样进入选择框：** ModelControls 挂载后请求 `GET /api/v1/models`，接口调用 `ModelService.list_models`，其中 `builtin_models` 生成预设列表。`default` 显示为“硅基流动（默认）”，复用 main.py 创建的图；当 `DeepSeeK_API_KEY` 非空时，额外返回 `id="builtin:deepseek"` 的“DeepSeek 官方”选项。选择它后，下次聊天 JSON 携带 `model_id="builtin:deepseek"`；`resolve` 专门读取 `DEEPSEEK_CHAT_MODEL`（默认 `deepseek-flash`）、`DeepSeek_BASE_URL` 和 `DeepSeeK_API_KEY`，构建 ModelSpec，再由 `runtime_graph` 装配本次请求的图。硅基流动的额外预设仍使用硅基流动凭据，两个平台不能共用 Key。服务端的两个 Key 都不返回浏览器，不需用户再次手填。预算沿用服务端保守窗口配置，切换模型保持同一 conversation_id/thread_id；EmbeddingService 不读取 model_id，向量化仍使用硅基流动和 BAAI/bge-m3，因此切换回答模型不需要重新导入书籍。服务端预设不走自定义配置的解密分支，只有自定义配置才查用户归属并解密。

重点先看 [context.py](../backend/app/agents/context.py)，再回到 chat_graph.py 的 manage_context、plan、grounded_answer。这次新增的是会话内摘要，不是用户跨会话的长期记忆。

| 数据 | 保存在哪里 | 谁使用、为什么 |
| --- | --- | --- |
| messages | checkpoint 的完整消息列表 | 历史接口显示原对话，节点返回最终回答时仍追加到这里。 |
| conversation_summary | 同一 thread_id 的 checkpoint | 总结较早对话，帮助补全“它”“之前提到的”等指代，不作为书籍证据。 |
| summarized_count | 同一 thread_id 的 checkpoint | 已摘要的用户/AI 消息数量；下次从这个位置继续，避免重复总结整个历史。 |
| context_messages | 每次请求重新准备，作为状态字段保存 | 预算内的近期原文，供改写和回答使用；与 messages 是不同列表。 |
| Store 中的用户记忆 | users/user_id/memories | 跨会话的学习偏好等信息；当前摘要节点不会写入这里。 |

先读 text_tokens、message_tokens：这里用 UTF-8 字节数估算，并为消息角色预留开销。这样对中文比“每四个字符一 token”保守；它不是所选模型的精确 tokenizer。再读 recent_start：从最后一条问题向前取近期消息，控制总预算，并尽量从用户消息开始。最新问题自身太长时直接给出中文提示，不把半个问题交给模型。

~~~python
# chat_graph.py：在本轮规划之前执行，旧会话缺少摘要字段时使用默认值。
return await context_manager.prepare(
    state["messages"],
    state.get("conversation_summary", ""),
    state.get("summarized_count", 0),
)
~~~

ContextManager.prepare 先取得完整用户/AI 消息，然后从 summarized_count 之后计算未摘要消息及已有摘要的长度。默认超过 6000 单位才进入摘要分支；先选择最多八条且预算内的近期消息，再将更早部分分批交给摘要模型。单条很长的旧消息也会分段，防止摘要请求自己超限。每批结果与已有摘要合并；只有对应批次全部成功，游标才前移。失败时保留已完成进度，不删除原文，下轮还能重试未完成部分。

~~~python
# context.py：只返回模型视图与摘要，不更新或删除 messages。
return {
    "conversation_summary": summary,
    "summarized_count": cursor,
    "context_messages": active[start:],
}
~~~

然后看 plan：首轮直接使用原问题。有前文时将“摘要＋预算内近期原文”传给 SearchPlan 模型，不再以领域关键词跳过追问，并要求保留数量、版本和专业名词。改写失败回退原问题。生成摘要和改写问题都可能丢失信息或误解指代，测试只能验证代码链路，真实效果还需多轮问题评测。

最后看 grounded_answer：系统消息仍包含本轮书籍原文和证据规则，后面加会话摘要提示，再加 context_messages。完整历史留在数据库，模型只看受限视图。

~~~python
messages = [
    SystemMessage(content="本轮系统规则与书籍证据……"),
    *summary_message(state.get("conversation_summary", "")),
    *state["context_messages"],
]
ensure_input_budget(messages, limits.CHAT_MAX_OUTPUT_TOKENS, limits)
async for chunk in model.astream(messages, max_tokens=limits.CHAT_MAX_OUTPUT_TOKENS):
    # 这里仍是原有实时输出；摘要和改写的文字不转发给前端。
    ...
~~~

输入预算不是只限制历史：retrieve 也按 RAG_CONTEXT_BUDGET_TOKENS 选择能完整容纳的切片，再重新编号。完整切片不能放入时跳过，不把截断的半段当作完整来源。核对模型仍只读取本轮问题、这些书籍原文及候选答案，摘要不是核对证据。长问题或配置不合适时 ensure_input_budget 在调用前拒绝；流式接口发中文 error，普通接口返回 422。

| 配置 | 默认值 | 作用 |

## 第四条完整数据链：回答怎样保存并返回页面

main.lifespan 创建 Postgres checkpointer 与 Store，并在 build_chat_graph 时注入。checkpointer 按 thread_id 保存图的消息；Store 用用户 namespace 保存长期记忆。两者虽然都用 PostgreSQL，却解决不同问题。get_chat_history 先校验会话归属，再用 thread_id 调 graph.aget_state，从 checkpoint 取消息。save_memory 只从用户消息判断是否存入长期记忆，不能把它当作书籍证据。

chat_stream 使用 graph.astream(stream_mode=["custom", "updates"])。grounded_answer 内部使用 model.astream，每收到一个文本增量，就通过 get_stream_writer() 发送 token；custom 模式把它交给 event_stream，立即转换为 SSE 并让前端追加文字。只转发回答模型的文字，不转发规划、核对或记忆模型的输出。

retrieve 节点完成时，API 先从 updates 中取得 sources，发送带 pending=true 的 sources 事件；前端接收候选来源，但默认只显示回答。随后模型开始流式生成，最终 sources 事件确认或清空候选来源。有最终来源的回答下方显示“展示详情”，点击后展开该回答的参考文献卡片及原文摘录，也可收起；顶部知识库旁不再有全局详情按钮。

~~~python
writer = get_stream_writer()
combined = None
async for chunk in model.astream(messages):
    combined = chunk if combined is None else combined + chunk
    if chunk.text:
        writer({"type": "token", "content": chunk.text})
~~~

模型生成结束后，仍调用 evidence_supports_answer 核对完整候选回答。grounded_answer 返回通过核对的 AIMessage 或固定弃答；API 从 updates 模式取得该节点结果，发送 answer 事件覆盖草稿，再发送 sources。无依据分支没有模型增量，直接发送最终弃答。整个图执行完成后发送 done；异常发送 error，前端清除未完成的草稿。前端在生成和核对期间显示状态，历史只保存最终答案。实时草稿可能含不受证据支持的内容，已经展示过的文字无法撤回；这是当前流式体验与事后核对的取舍。

自己画出三条线：model.astream → writer → graph.astream → SSE → 前端追加草稿及替换最终答案；thread_id → checkpoint → 历史消息；user_id → Store namespace → 长期记忆。说明 token、status、answer、sources、done、error 各自的作用。

## 失败分支：面试时不要只讲成功路径

| 场景 | 具体代码怎么处理 | 应解释的原因 |
| --- | --- | --- |
| 用户名或邮箱重复 | UserService 查重，auth.register 将 ValueError 转为 409。 | 把业务冲突明确传给调用方；数据库唯一约束也承担最后防线。 |
| token 无效或用户已不存在 | get_current_user 解码或查用户失败，返回 401。 | token 中的 ID 还要对应现存用户。 |
| 请求别人的会话或书 | ConversationService.get_owned 或 KnowledgeBookRepository.get_owned 按当前用户校验，接口返回 404。 | 避免仅凭有效登录态越权读取他人资源。 |
| 上传格式、大小或重复文件不合规 | KnowledgeService.upload 校验后抛 ValueError，knowledge.upload_book 返回 400。 | 在安排昂贵的解析和向量化前拒绝无效输入。 |
| 解析或向量化失败 | KnowledgeService.process 记录异常、尝试清理该书向量，并把 KnowledgeBook 标为 failed、保存 error。 | 三个存储没有共同事务，必须让失败可见、可重试。 |
| 服务在处理书籍时重启 | mark_interrupted_imports 把遗留 processing 标为 failed，用户可重试。 | 进程内后台任务不会自动跨重启恢复。 |
| 检索没有片段 | route_from_retrieval 走 no_evidence，返回固定弃答。 | 没有书籍证据就不调用模型用常识编答案。 |
| 有命中但回答没有足够依据 | citations_valid 或模型核对失败，grounded_answer 返回固定弃答、sources 置空。 | 相关片段可能不足以支持具体结论。 |
| 长期记忆保存失败 | save_memory 记录日志并返回空更新，本次回答仍可返回。 | 可选的用户记忆不应让已核对的书籍回答失败。 |

## 项目当前边界：回答“做到了什么”，也要能说“尚未做到什么”

- 已有书籍解析、切分、向量化、Milvus 检索、来源引用与依据核对；扫描版 PDF 没有内置 OCR，需要先获得可提取文本。
- 图中使用 search_book_chunks 工具，但节点按固定路径调用它；这展示了工具封装与 LangGraph 编排，不应描述为会自主选择任意工具的开放式 Agent。
- 长期记忆有保存与读取接口；当前书籍回答的证据仍来自 Milvus 片段，不能把用户记忆说成书籍来源。
- SSE 实时转发 model.astream 的文本增量；草稿标记为待核对，最终核对结果覆盖草稿。用户可能看到尚未得到证据支持的内容，不能声称所有实时文字都已核对。
- BackgroundTasks 是进程内任务。当前用 processing/failed 状态与重试应对中断；若要处理更大规模的导入，还需持久队列等机制。
- 自动评测覆盖有限样本，依据核对本身也依赖模型判断，所以只能说“降低无依据回答的风险”，不能承诺零幻觉。

这些节点定义在 [chat_graph.py](../backend/app/agents/chat_graph.py) 的 build_chat_graph 内部。调用者是编译后的 LangGraph，而不是 FastAPI 逐个手工调用节点。先看文件末尾 add_node/add_edge，再逐个看函数如何读取 ChatState、返回要更新的字段。

| --- | --- | --- |
| build_chat_graph | model＋checkpointer＋store → 已编译 graph。 | main.lifespan 调用一次并放入 app.state.chat_graph；evaluate_live 用 InMemorySaver 创建评测图。 |
| manage_context | 完整 messages＋摘要游标 → 会话摘要、游标和预算内 context_messages。 | START 后运行；分批总结未处理旧消息，不删除完整历史。 |

### 8. 前端只需知道的调用点

最后再看 [App.tsx](../frontend/src/App.tsx) 的 App、Login.submit、Chat.send、KnowledgePanel.upload 和 [api.ts](../frontend/src/api.ts) 的 api、uploadBook、streamChat。App 决定显示登录页或聊天页；Login.submit 发送登录或注册 JSON；Chat.send 首次发问先创建会话，再把 conversation_id 和 message 交给 streamChat；KnowledgePanel.upload 把 File 包成 FormData。api 负责普通 JSON 请求和 Bearer token，uploadBook 负责 multipart，streamChat 负责读取 SSE。前端函数都不直接调用 Python 函数，它们通过 HTTP 路由进入上表的接口函数。

阅读任何一行时，可以用同一个模板做笔记：**函数名 → 调用者 → 参数的具体例子 → 返回值/状态变化 → 下一位接收者 → 异常分支**。例如 KnowledgeService.search：工具调用它；传入 session、user_id=7、question="什么是 Store？"；得到 list[RetrievedChunk]；tools.search_book_chunks 把它转成字典；没有 ready 书时返回空列表，随后图走 no_evidence。
